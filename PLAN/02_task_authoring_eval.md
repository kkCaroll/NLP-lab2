# 评估：把小型代码修复任务的构造交给 DeepSeek-V4.1-Flash

> 评估日期：2026-10-20
> 相关文件：`00_experiment_plan.md`、`models/MODELS.md`、`models/models.json`

## 结论

**可以让 flash 做“受约束的草稿与 bug 注入”，但不建议让它“全权造题并自己定稿”。**

推荐的分工是：

1. **正确代码、测试、issue 描述**由**不参与评测的模型**（DeepSeek-V4-Pro）或人完成；
2. **flash 只负责在正确代码上生成候选 bug 注入 diff**（3 个候选/题）；
3. 自动验证器筛选；
4. **V4-Pro 盲解**做独立难度与可解性校准；
5. 人工复核后冻结。

这样既利用了 flash 的低成本，又避免了“被测模型同时出题、写答案、判卷”的自博弈偏差。gold patch 由注入 diff 反向得到，天然最小。

基础代码可以进一步复用现有基准，以降低编写成本。标准题优先使用 QuixBugs 与 BigCodeBench 标准库任务，困难题使用 BigCodeBench 改造或原创多文件项目。来源评估与 24 题分配见 [01_task_source_eval.md](01_task_source_eval.md)。复用基础代码不改变上述分工原则，测试、issue 和 gold 仍由非被测方控制。

如果坚持让 flash 全权造题，则必须补上 **V4-Pro 盲解 + 人工全量复核**，并在论文的 Threats to Validity 中明确披露“题目作者与部分被测模型同源”。**最不推荐**的是 flash 单独造题、无独立复核、直接进入主实验。

## 1. 为什么“被测模型造题”有风险

| # | 风险 | 具体表现 | 对实验的威胁 | 能否自动检测 |
|---|---|---|---|---|
| R1 | 自评估/自博弈偏差 | flash 按自己的代码风格、常见错误模式出题，可能无意中让 flash 更容易 | 模型间比较被污染；flash 的通过率被高估 | 否 |
| R2 | 解法泄漏 | issue、注释、变量名、测试名、commit message 中残留修复提示 | 修复成功率虚高，反馈条件差异被压缩 | 部分 |
| R3 | gold 非最小 | flash 先写 buggy 代码再单独写“参考修复”，两者风格/范围不一致 | EditRatio、过修改率失真 | 是（行数/文件数门槛） |
| R4 | 测试质量差 | 目标测试只检查“不抛异常”；回归测试与实现耦合；测试本身有 bug | 题目无效、结果不可解释 | 部分 |
| R5 | 回归覆盖不足 | 回归测试没有覆盖共享 helper 或相邻分支，模型大改也不失败 | 过修改/回归率被低估 | 部分（覆盖率+扰动） |
| R6 | 难度标定循环 | “困难”由 flash 自己判断，实际对 flash 不难 | 难度分层失效；反馈分支样本不足 | 否（需盲解校准） |
| R7 | 多样性不足 | 24 题都是同一类“改一个运算符” | 外部效度低；类别分析无意义 | 否（需人工/统计） |
| R8 | 污染/记忆 | 题目改编自公开 benchmark 或常见教程，模型见过 | 通过率虚高 | 部分（来源审查） |
| R9 | 生成不稳定 | 同一 spec 多次生成质量波动大；测试 flaky | 不可复现 | 是（重复运行/确定性检查） |
| R10 | 作者与评测同源（meta-bias） | 本次规划助手本身也是 flash；规划、出题、被测三者同源 | 审稿人可质疑全链路偏差 | 否（只能披露+外部复核） |

R10 值得单独说明：当前会话的助手模型就是 `deepseek-flash`。因此本文档的评估**不是独立评估**，而是“被测模型对自身出题方案的自我评估”。这不能替代人工复核，也不能替代 V4-Pro 的盲解校准。报告中应如实写明这一点。

## 2. 哪些环节可以自动化，哪些不能

### 2.1 可以自动化的硬门槛（建议实现为 `validate_task.py`）

对每个任务在 buggy 态和 gold 态各跑一遍，全部通过才允许入库：

| 门槛 | 检查内容 |
|---|---|
| G1 结构 | 源码可导入；只依赖标准库；无网络、无随机、无当前时间依赖；AST 可解析 |
| G2 双态 | buggy 态：目标测试失败；gold 态：**全部**测试通过 |
| G3 失败原因 | buggy 态的目标测试必须是 assertion failure/明确的行为错误，不能是 ImportError、CollectionError、SyntaxError |
| G4 回归基线 | 所有 regression tests 在 buggy 态通过（证明它们是“原本通过”的） |
| G5 gold 最小 | gold 只改允许的文件；不碰 tests/、配置、依赖；改动行数 ≤ 题设预算（标准题 ≤ 8 行，困难题 ≤ 15 行） |
| G6 测试只读 | gold diff 中不含测试文件；harness 运行后恢复测试并校验 SHA-256 |
| G7 确定性 | 同一状态连续跑 5 次，结果完全一致；无 skip/xfail；全套 < 10 秒 |
| G8 泄漏扫描 | 源码/issue/测试名中不含 `BUG`、`FIXME`、`TODO: fix`、`intentional`、题号、gold 片段；git 历史中不含 gold 提交 |
| G9 覆盖 | 目标测试实际执行到 bug 所在行；回归测试覆盖被修改文件及共享 helper |
| G10 反过拟合 | 一个语义等价的替代修复也能通过；一个错误修复必须失败（防止测试只认某一种写法） |
| G11 元数据 | 题号、类别、难度、允许编辑范围、gold 行数、测试清单齐全 |
| G12 规模 | 标准题 2–4 个源文件 / 100–250 行；困难题 4–8 个源文件 / 250–600 行；回归测试 ≥ 5 个 |

### 2.2 不能自动化、必须人看的部分

- **真实性**：这个 bug 像不像真实开发者会写出来的？
- **自然性**：issue 像不像用户/同事写的？有没有“考试腔”？
- **歧义性**：仅凭 issue + 代码 + 失败日志，能否确定期望行为？
- **难度语义**：困难是因为“跨文件定位/共享 helper 干扰”，还是因为题目本身没说清？
- **多样性**：24 题是否覆盖了要求的 7 类错误，且没有大量同构题？
- **可解性**：V4-Pro 盲解失败时，是题太难，还是题有问题？

## 3. 推荐流水线（gated pipeline）

```
[我们] 写 task spec（类别/难度/文件/行为/允许范围/行数预算）
        │
        ▼
[V4-Pro 或人] 写正确代码 + 目标测试 + 回归测试 + issue
        │
        ▼
[flash] 在正确代码上生成 3 个候选 bug 注入 diff
        │
        ▼
[validate_task.py] G1–G12 自动筛选，最多 2 轮修复
        │
        ▼
[V4-Pro] 盲解（只看 issue + buggy repo，不看 gold，同工具预算）
        │
        ▼
[人] 复核真实性/歧义/多样性/泄漏
        │
        ▼
[冻结] git tag + SHA-256 manifest + 禁止再改
```

### 3.1 角色分工

| 角色 | 负责 | 不负责 |
|---|---|---|
| 我们（人） | task spec、验收标准、最终签字 | 不直接写所有代码（可用 V4-Pro 起草） |
| V4-Pro（非被测） | 正确代码、测试、issue 初稿、盲解校准 | 不参与被测模型的反馈实验 |
| flash（被测） | 候选 bug 注入 diff | **不写测试、不写 issue、不定难度、不定 gold** |
| 自动验证器 | G1–G12 | 不判断真实性与歧义 |
| 人 | 全量复核、冻结 | — |

关键点：**flash 只看得到正确代码和测试，看不到实验假设、反馈条件、其他模型的运行结果。** issue 由 V4-Pro/人根据 spec 写，不由 flash 写，切断“出题人把答案写进题面”的路径。

### 3.2 为什么“正确代码 + 测试先行”更好

- gold patch = 注入 diff 的**反向 diff**，行数和范围天然可控，直接满足 R3。
- 测试由非被测方写，避免“测试只认 flash 自己的实现”（R4）。
- flash 的任务被压缩成“找一个能让目标测试失败、但不破坏回归测试的最小改动”，这是一个**受约束的搜索**，比“从零造一个题”容易验证得多。
- 困难题可以通过“把 bug 注入到共享 helper/跨文件调用链”来制造定位难度，而不需要让 gold 变大。

### 3.3 bug 注入提示词模板（给 flash）

```text
你在一个已经全部测试通过的小型 Python 仓库中工作。
任务：注入一个真实、隐蔽、最小的 bug，使得：
1. 只有 tests/test_target.py::<TARGET_TEST> 失败；
2. tests/test_regression_*.py 中的全部测试仍然通过；
3. 不修改任何测试文件、配置文件、依赖；
4. 不添加任何注释、TODO、FIXME 或暗示性命名；
5. 改动不超过 <N> 行，只允许修改 <ALLOWED_FILES>；
6. bug 必须是“行为错误”，不能是语法错误、导入错误或让测试收集失败。

请给出 3 个互不相同的候选，每个候选包含：
- unified diff
- 一句话说明它改变了什么行为（不要写“这是 bug”）
- 预计哪条断言会失败

不要修改文件，只输出 diff。
```

拿到 diff 后由 harness 应用、验证、反向得到 gold。flash 不直接落盘，避免它“顺手修好”或改测试。

### 3.4 盲解校准（V4-Pro）

- 输入：issue + buggy repo + 失败日志；**不给 gold、不给注入说明、不给题号**。
- 工具/步数/时限：与主实验一致，保证可比。
- 记录：是否通过、轮次、工具调用数、耗时、是否运行测试、是否改测试。
- 判定：
  - 标准题：V4-Pro 应在 1–3 轮内通过；若 3 轮都失败，题面可能歧义或过难，退回重写。
  - 困难题：V4-Pro 可以通过，但应表现出更多定位步骤；若一眼秒过，说明“困难”标签不成立。
  - 若 V4-Pro 靠改测试通过，直接废弃该题（G6 已拦，但盲解可再次暴露）。

注意：V4-Pro 比 flash/GLM 强，它的通过不代表被测模型会通过；它只用来排除“无解/歧义/太易”的题，不用来预测主实验通过率。

## 4. 三种方案对比

| 方案 | 质量 | 作者偏差 | 成本 | 人工 | 建议 |
|---|---|---|---|---|---|
| A. flash 全权造题（代码+测试+issue+gold） | 中–低 | **高** | 最低 | 少 | 不推荐 |
| B. flash 全权 + V4-Pro 盲解 + 人工复核 | 中–高 | 中 | 低 | 中 | 可接受，需披露 |
| C. 正确代码/测试由 V4-Pro/人写，flash 只做 bug 注入 | **高** | **低** | 中 | 中 | **推荐** |
| D. V4-Pro 全权造题 + 人工复核 | 高 | 低 | 中–高 | 中 | 预算允许时推荐 |

如果时间紧，推荐一个折中：

- **12 道标准题**：用方案 C，flash 注入 bug，成本低、验证快；
- **12 道困难题**：用方案 D，V4-Pro/人写正确代码与测试，flash 仍可提供 bug 候选，但由人选定；
- 全部题目经过 G1–G12 + V4-Pro 盲解 + 人工签字。

这样困难题的“定位难度”不会被 flash 的生成能力上限卡住，标准题又能利用 flash 的低成本。

## 5. 成本与时间估算

| 项目 | 估算 |
|---|---|
| flash 生成 bug 候选 | 24 题 × 3 候选 ≈ 72 次短生成，< ¥5 |
| V4-Pro 写正确代码+测试+issue | 24 题 × 1–2 次，约 ¥20–50（或人工 1–2 天） |
| V4-Pro 盲解 | 24 题 × 1–3 轮，约 ¥10–30 |
| 自动验证/返修 | 脚本 + 2 轮重试，主要是机时 |
| 人工复核 | 3–5 小时（困难题全看，标准题抽 50%+全看高风险题） |
| 总计 | 1–2 个工作日，¥50–100 量级（不含人工） |

对比方案 A：token 更便宜，但返修和人工复核更多，且作者偏差无法用钱消除。

## 6. 对主实验设计的影响

1. **主实验仍然成立**：题目在正式运行前冻结，反馈条件在运行时才施加，不存在“运行时泄漏”。
2. **模型间比较要谨慎**：如果 flash 参与了出题，即使只做注入，也应在论文中写“DeepSeek-V4.1-Flash 参与了题目构造（bug 注入），但未参与测试/issue/gold 的定稿；V4-Pro 盲解与人工复核用于降低作者偏差”。
3. **不要用被测模型校准难度**：不要根据 flash/GLM 的 pilot 结果反复调题，否则会变成对模型调参。只允许按预注册的 floor/ceiling 规则替换“两模型都首轮通过”或“两模型都完全无进展”的题，并记录替换原因。
4. **保留审计痕迹**：每题保存 spec、注入 diff、gold、验证器输出、V4-Pro 盲解记录、人工签字；冻结后任何修改都要写 changelog。

---

## 7. 最终建议

- **推荐方案 C**：V4-Pro/人写正确代码与测试，flash 只做受约束的 bug 注入，自动验证 + V4-Pro 盲解 + 人工复核。
- 若必须把“造题”整体交给 flash，采用**方案 B**，并把作者偏差写进限制；不要用方案 A。
- 无论选哪种，**24 题全部人工过一遍**；至少困难题和所有“首轮通过/首轮完全无进展”的题必须人工看。
- 本次评估由 flash 自己完成，属于自我评估；最终以人工复核和 V4-Pro 盲解为准。
