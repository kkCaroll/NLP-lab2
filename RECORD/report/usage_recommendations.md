# 使用建议

## 给代码智能体的反馈

1. 不要只表达不满。单纯负面措辞在实验中与较低的修复成功率相关，且常伴随未编辑失败。
2. 优先给出方法指令，例如先读错误日志、定位调用方、做最小必要修改。
3. 同时说明期望行为与禁止行为，例如不要修改测试、不要改无关文件。
4. 若上一轮没有产生修改，直接指出这一点，并要求先给出定位结论再编辑。
5. 若上一轮改错，指出具体失败测试与错误行，不要只重复负面评价。

## 环境设置

1. 允许运行目标测试与回归测试，但给测试调用单独预算，避免测试消耗全部工具调用。
2. 给读取、搜索与编辑分别计数，识别预算耗尽与未编辑失败。
3. 回归测试应覆盖非目标文件，并用变异测试检查敏感性。零回归不等于无回归。
4. 对同一任务重复运行，至少区分条件效应与运行间波动。

## 评价智能体

1. 不要只看平均修改行数。低修改量可能是精确，也可能是停滞。
2. 同时报告是否编辑、是否通过、是否引入回归与修改范围。
3. 对高通过率模型注意天花板效应，对低通过率模型注意预算截断。
4. 将负面反馈的效果与任务难度、模型能力和条件顺序分开分析。
